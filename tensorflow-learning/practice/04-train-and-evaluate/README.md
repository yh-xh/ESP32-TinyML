# 验证集、过拟合和 EarlyStopping

上一节最后留了一个问题：训练 loss 很低，模型就真的好吗？

不一定。模型可能只是把训练数据背下来了。这一节故意让过拟合发生：训练 loss 一路降到接近 0，验证 loss 却在某个 epoch 之后开始变差。

代码里每个 API 和参数都有注释；这份文档讲的是：为什么这样分数据、曲线怎么看、什么时候该停。

## 数据怎么分

```text
训练集：6 个点
验证集：200 个点，密集覆盖 [0, 2π]
测试集：200 个随机点
```

- 训练集：更新参数；
- 验证集：每个 epoch 结束算 `val_loss`，参与 EarlyStopping / ModelCheckpoint 的决策；
- 测试集：训练和调参都不看，最后只评估一次。

训练集只有 6 个点，是故意的。模型有 1,153 个参数，参数量远大于数据量，它完全可以把 6 个点背下来。真实项目不会这么极端，但判断方法是同一套。

为什么不用 `validation_split=0.2`？因为这里的 `x` 是按大小排好序的，Keras 会取最后一部分，验证集就只剩区间尾部，不能代表整个 `[0, 2π]`。真实数据如果排好序，记得先打乱再切。

验证集和测试集都用干净的 `cos(x)`，没有加噪声。这样能看清模型是学到了曲线，还是只在训练点上背答案。真实项目里验证集通常也有噪声，但过拟合的判断逻辑一样：训练 loss 和验证 loss 的走势分叉。

## 模型和回调

模型还是：

```text
1 -> 32 -> 32 -> 1
```

回调做两件事：

- `EarlyStopping`：盯 `val_loss`，连续 50 轮没改善就停，并恢复到最好的权重；
- `ModelCheckpoint`：每次 `val_loss` 创新低，把模型保存到 `best_model.keras`。

`patience=50` 的意思是“给 50 轮观察窗口”。太小可能错过后面的改善，太大则浪费时间。

## 实际输出

```text
--- summary ---
epochs run: 205
best epoch: 155
best val MSE: 0.00813639722764492
last epoch train MSE: 7.207765975181246e-06
last epoch val MSE: 0.010385973379015923

MSE after restoring best weights:
train: 0.002497380133718252
val:   0.00813639722764492
test:  0.008079256862401962
baseline test MSE (always predict train mean): 0.5476971864700317
```

逐行读：

- 第 155 轮验证 loss 最低；
- 之后 50 轮没有改善，所以第 205 轮早停；
- 最后一轮训练 loss 已经到 `7.2e-06`，6 个点基本被记住了；
- 最后一轮验证 loss 是 `0.0104`，比最好时的 `0.00814` 更差；
- EarlyStopping 把权重恢复到第 155 轮，所以恢复后的训练 MSE 是 `0.0025`，不是 `7.2e-06`；
- 恢复后验证 MSE `0.00814`，测试 MSE `0.00808`，两者很接近；
- 一直预测训练集平均值的 baseline 是 `0.5477`，模型确实学到了东西。

注意区分：

```text
last epoch train MSE      第 205 轮的权重
MSE after restoring       第 155 轮的权重
```

这两个数不一样，是因为 EarlyStopping 不要最后一轮。

## 怎么看图

左边是 loss：

```text
训练 loss：一路下降，最后到 1e-6
验证 loss：先降，约第 155 轮见底，之后变差
```

两条线后期分叉，这就是过拟合：

- 模型对训练点越来越熟，训练 loss 越来越低；
- 但这种“熟”没有变成泛化能力，验证 loss 反而变差。

右边是预测：

- 红点是 6 个训练点，模型基本都穿过了；
- 蓝线是真实 `cos(x)`，橙线是模型预测；
- 橙线在谷底附近多拐了一点，和蓝线不完全重合。

数据越少、模型越大，这种额外弯曲越容易发生。

## 训练和验证是同时跑的吗

不是。它们在一个 `fit` 调用里，但是串行的：

```text
1. 训练集分 batch
2. 每个 batch：前向 -> 算 loss -> 反向传播 -> 更新参数
3. 训练集跑完，验证集前向一遍，算 val_loss
4. EarlyStopping / ModelCheckpoint 看 val_loss
5. 下一个 epoch
```

- 训练更新参数；
- 验证只做前向，不更新参数；
- 验证用的是这一轮训练结束后的权重；
- 两个数据集不是并行计算，而是一个跑完再跑另一个；
- 所以总时间包含验证的时间。

## EarlyStopping 恢复权重，算不算用验证集调参

算，虽然它不更新梯度。

这里有两件事：

- **更新参数**：用训练集的梯度改 W 和 b；
- **模型选择**：用验证 loss 决定停在哪轮、保留哪组权重。

EarlyStopping 做的是第二件。它没有拿验证集做反向传播，但它在 205 个 checkpoint 里挑了验证 loss 最低的那个。最终留下的权重，是“验证集认为最好”的那组。

这也是为什么验证 loss 会略微偏乐观：你在一串带随机波动的验证 loss 里挑了最小值。测试集完全不参与这种挑选，所以它给的估计更独立。

## 常见问题

### 验证 loss 一定会先降后升吗

不一定。数据多、模型小、任务简单时，验证 loss 可能一直降，最后和训练 loss 很接近，这说明没有明显过拟合。

典型信号是：训练 loss 还在降，验证 loss 已经不再改善，甚至开始上升。看趋势，不要盯某一个 epoch 的抖动。

### 为什么验证 loss 会波动

验证集只有 200 个点，每个 epoch 的权重略有不同，预测也会变。单点抖动很正常，所以 EarlyStopping 用“连续 patience 轮没改善”判断，而不是一上升就停。

### 测试集能不能用来调 patience

不能。调 `patience` 只能用验证集。测试集只在最后评估一次，否则它就不再是“没见过的数据”。

### 为什么恢复后训练 MSE 不是 7e-6

因为恢复的是第 155 轮。那一轮训练 loss 还有 `0.0025`，到第 205 轮才降到 `7e-6`。EarlyStopping 故意不要第 205 轮，因为那一轮验证 loss 更差。

### 为什么纵轴用 log

训练 loss 从 `1` 降到 `1e-6`，跨度六个数量级。线性刻度下后面的变化几乎看不见；log 刻度能同时看清前期下降和后期分叉。

### 为什么 `monitor="loss"` 不行

训练 loss 几乎一直在降。监控它，EarlyStopping 基本不会触发，最后只会跑满 `epochs`，得到一个过拟合的模型。

### 脚本跑得慢

每个 epoch 都要在 200 个验证点上算一次 loss，这部分有开销。这一节大约几十秒。觉得慢可以把验证集降到 100 个点，或者把 `epochs` 上限调小；但别把 `patience` 调得太小。

## 顺手改两下

1. 训练点改成 12 个：数据变多，过拟合会减弱；
2. `patience=10`：更早停，看验证 loss 是不是更差；
3. `restore_best_weights=False`：保留最后一轮，测试 MSE 应该更差；
4. 去掉 EarlyStopping，只留 ModelCheckpoint，跑满 500 轮；
5. `monitor="loss"`：体会“监控错指标”的后果；
6. 给训练集加噪声：训练 loss 和验证 loss 的差距会更明显。
